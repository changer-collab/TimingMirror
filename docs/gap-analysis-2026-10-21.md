## 0. 结论摘要

### 0.1 五条结论

1. **v2 的核心判断仍然成立，且比 v3 更聚焦。** v2 是“诊断优先”：先用幽灵线把损耗算给用户看，再用 Agent 解释、用提醒帮助改变。v3 增加“规则共建/契约”作为行动层，方向自洽，但它不能替代诊断主线。当前项目的问题不是“功能少”，而是**诊断主线没有接到用户端**。
2. **v2 的 7 项 P0 没有一项按原验收标准完整兑现。** 幽灵双面板只在开发者报告；瀑布图只有引擎；损耗排行没有；四指标卡只兑现约三张；真 LLM 自由问答只支持一个问题；芯片只有 1 个；交易前提醒只有历史情境模拟。相对最接近的是“四指标卡”和“交易前模拟”。
3. **定位在文档层清楚，在产品层不清楚。** 文档里是“镜子，不是老师”；首页却把最锋利的因果判断换成了中性的对照问题。真实报告又拿掉了“为什么”和“哪一笔”。用户能看到“我比买入不动少赚”，但看不到“我选的股票在涨，是操作把钱吃掉了”——后者才是 v2 的定位。
4. **痛点本身够痛，但产品还没把“痛”变成“信”。** 真金白银、反复发生、可量化、可归因，这四点都成立。缺的是：真实报告中“股票本身涨幅”缺位或口径混同、“最错一笔”无法回答、行为模式没有清单。用户只知道“我少赚了”，不知道“我为什么少赚、下一次怎么少犯”。
5. **交付风险已经出现。** 最新 main 的 `npm run check` 是红的；README 严重过期；动态行情路径与 R2/F-3/R5 冲突；M0 八类接口仍未冻结；当前发布站是 Qoder Site，不是 v3 要求的阿里云 OSS+函数计算。距材料提交约 4 天，必须先收口核心叙事，而不是继续加模块。

### 0.2 v2 P0 完成度

| v2 P0 功能 | 当前实现 | 完成度判断 |
|---|---|---|
| 幽灵对比线（双面板） | 开发者报告有单标的 S1 幽灵线；用户真实报告没有 | 未进入用户路径 |
| 核心指标卡（实际/对照/损耗 pp+元/股票本身涨幅） | 演示报告有 4 张，但“标的自身涨幅”与买入不动收益同为 +18.92%；真实报告第四张是“买入成本” | 部分兑现，第四卡失真 |
| 择时损耗瀑布图 | `decompose.js` 引擎存在，未接入任何用户视图 | 仅引擎 |
| 损耗排行表 | 无实现 | 未实现 |
| 真 LLM 自由问答 | 仅支持“组合整体表现如何？”四类事实；其余本地拦截 | 约 1/4 兑现 |
| 报告解读预设问题（4–5 个芯片） | 只有 1 个芯片 | 部分兑现 |
| 交易前提醒弹窗 | 规则页有历史情境模拟；代码明确“不是盘中实时提醒” | 演示替代，不是真实交易前 |

**判断：v2 P0 应按“叙事验收”而不是“代码存在”来计分。** 引擎、规则、复核的代码量很大，但用户打开真实报告时看不到幽灵线、瀑布、排行和逐笔归因，v2 的核心承诺就没有兑现。

### 0.3 当前最强的部分（不要推翻）

- **导入能力超出两版原案**：CSV/TSV/XLSX/PDF/文本/截图，本地解析、PDF 渲染、AI 纠错、视觉识别、草稿编辑、逐条校验。这是真实工程资产。
- **计算与复核引擎扎实**：实际/幽灵/损耗、S1 单笔卖出替换、逐日双路径、损耗分解、独立复核、provenance、悬空引用阻断。
- **规则页有完整骨架**：三种模板、自然语言识别、确认/改写/拒绝、版本记录、适用范围、历史情境触发/不触发/缺数据语义。
- **在线复述的边界处理正确**：8 秒超时、离线兜底、本地数字子集校验。
- **测试体量大**：37 个套件、约 1579 项通过检查、316 项前端冒烟（但当前有 1 个套件失败，见 §4.5）。

这些是“守住下限”的资产。问题在于它们没有围绕 v2 的第一眼价值组织起来。

## 1. v2 与 v3 的关系：以谁为主

### 1.1 两版差异

| 维度 | v2 原案（用户） | v3 融合版（组长） | 对当前项目的含义 |
|---|---|---|---|
| Slogan | 你亏的不是股票，是操作。 | 你亏的不是选股，是择时。 | v2 更贴近产品实际测量的“操作”；v3 更锋利但更窄。必须二选一，不能混用。 |
| 一句话定位 | 用自己的历史交易数据，算清实际收益与买入持有收益的缺口，让股民第一次看见择时行为值多少钱。 | 一个听得懂你的问题、拿得出案例的交易行为智能体——损耗归因到每一笔；相似情境再现，提醒你回看。 | v2 更具体、可验收；v3 更强调 Agent，但当前 Agent 能力支撑不了这句话。 |
| 主叙事 | 诊断：幽灵线 → 看见损耗。 | 看见 → 守住：幽灵线 → 规则共建 → 交易前契约警告。 | v3 更完整，但当前实现是“守住”做得比“看见”深，顺序倒了。 |
| 产品结构 | Dashboard + Agent。 | Dashboard + 契约 + Agent。 | 契约是增强，不应挤占诊断主线。 |
| P0 | 幽灵双面板、四指标卡、瀑布、排行、真 LLM、4–5 芯片、交易前提醒。 | 同上，CSV 升 P0，新增报告页立契约、合规标签、登记式应答。 | 两版在诊断 P0 上高度一致；当前缺口不是版本冲突，而是执行缺口。 |
| P1 | 行为画像、PGR/PLR、CSV、数据来源透视。 | 守约账本、数据来源透视、警告统计行。 | 可延后；不要为了 P1 牺牲 P0。 |
| P2 | 反事实沙盒、沪深 300 第三线。 | 决定自述冻结。 | 全部暂缓。 |
| 行情数据 | akshare 预拉 3 只股票 2023–2025 前复权缓存。 | 同样预拉缓存，演示前不实时调。 | 当前走同源函数动态 Tushare，是最重要的架构偏离。 |
| 部署 | GitHub Pages/Vercel + 轻量代理。 | 阿里云 OSS + 函数计算（赛事工具链约束）。 | 当前发布站是 Qoder Site，需确认是否合规。 |
| 周期 | 25 天。 | 15 天官方窗口。 | 压缩是当前“广度大、深度浅”的根因；只剩约 4 天，必须裁剪。 |

### 1.2 取舍建议

**以 v2 为主轴，保留 v3 的三项增强：**

1. **报告页 CTA → 规则**：这是 v3 最好的产品设计，把“看见”接到“守住”。但必须放在真实报告底部，不能只在演示报告里。
2. **来源/复核/合规标签**：v3 的“零幻觉自证 UI”是差异化，但当前真实报告没有。先做最小版：每个核心数字可展开公式、来源、复核结论；标签写实，不写“已过合规校验”这种无法证明的话。
3. **登记式应答**：用户说“帮我定止损”时，回答“这个我不能替你定；你定了的话，我帮你登记并追踪”。这是低成本、高记忆点的合规高光。

**原建议暂缓 v3 的 P1/P2（2026-10-22 更新）：** 守约账本、警告统计行、决定自述、PGR/PLR、反事实沙盒、沪深 300 第三线已在当前分支实现（见 §10）；完整 12 意图、相似情境检索、实时交易前提醒仍未实现。

### 1.3 必须统一的三个口径

1. **Slogan 二选一。** 建议主口径用 v2 的“你亏的不是股票，是操作。”——它覆盖追涨、杀跌、早止盈、过度交易，和产品实际测量的“操作损耗”一致；“择时”容易被理解为市场择时，窄了一截。若团队坚持 v3 的“选股/择时”，就全站统一，不要首页、PPT、README 各说一套。
2. **“交易前提醒”到底是实盘还是模拟。** 当前代码是历史情境模拟，不是盘中实时提醒。对外必须写“历史情境模拟”，不能写“下单前提醒”而不加限定。
3. **“股票本身涨幅”的定义。** 当前演示中它与买入不动收益相同（都是 +18.92%），说明它没有独立信息。必须定义清楚，否则这张卡就是重复计算。

## 2. 定位审计

### 2.1 各层实际在说什么

| 层 | 实际文案/行为 | 判断 |
|---|---|---|
| v2 PDF | “你亏的不是股票，是操作”；镜子不是老师；幽灵线是核心创新；Agent 三角色：翻译官/镜子/归因师 | 定位最锋利、最一致 |
| v3 PRD | “你亏的不是选股，是择时”；看见→守住；规则共建；Agent 对话+提醒双核 | 叙事更完整，但范围更大 |
| 报名 PPT | P2 三问痛点、P3 幽灵线四卡、P4 三创新点+Agent、P5 四层技术 | 承诺清楚，产品未完全对应 |
| 产品首页 | “你和‘买入不动’，差在哪里？”；“把交易照见成证据” | 中性、清楚，但缺少 v2 的因果钩子 |
| 演示报告 | “你的操作，比‘买入不动’少赚 ¥6,440”；四张卡，第四张“标的自身涨幅” | 视觉强，但第四卡与对照收益重复 |
| 真实报告 | “实际结果与买入不动的对照”；四张卡，第四张“买入成本” | 诚实但单薄，没有“为什么”和“哪一笔” |
| 对话页 | “只复述当前账单事实”“四项结果” | 从“Agent”退化成“数据查询器” |
| 规则页 | “规则工作区”“只做提醒” | 从“契约/承诺”退化成“规则管理” |

### 2.2 清楚的部分

- **产品名和核心比较对象清楚。** “择时镜子”“买入不动”“择时损耗”三个词能让人快速知道产品在做什么。
- **“镜子，不是老师”的边界清楚。** 不荐股、不预测、不替用户决定，这在首页、报告、对话里都有体现。
- **差异化清楚。** 券商复盘展示“你赚了多少”，镜子展示“你本可以赚多少”；这是 v2 最有效的定位句。
- **首页视觉资产强。** 右侧账本、幽灵线示意、差额数字，能在几秒内传达“同尺对比”。

### 2.3 不清楚/不一致的部分

| 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|
| 首屏缺少因果钩子 | 首页标题是“你和‘买入不动’，差在哪里？”，不是“你亏的不是股票，是操作” | 用户知道“在比较”，但不知道“为什么这件事重要”；评委记不住 | 把 v2 的钩子放回首屏，至少作为 kicker 或副标题 |
| 两个产品中心 | 诊断（幽灵线）与契约（规则）并列；当前规则/导入投入明显多于诊断 | “看见→守住”顺序倒置；用户还没看见就要求立规 | 先做诊断主线，契约作为报告页 CTA 的第二幕 |
| Agent 承诺过大 | 对话只支持“组合整体表现如何？”；其余本地拦截 | 评委任意提问会穿帮；“智能体”标签不可信 | 至少接 4–5 个芯片 + 越界兜底，再谈自由问答 |
| 交易前提醒承诺过大 | 仅历史情境模拟；代码明确“不是盘中实时提醒” | 被问“怎么接到券商下单”时无法回答 | 对外统一写“历史情境模拟”；演示时主动说明边界 |
| 演示与真实两套现实 | 演示报告 4 张卡、有 CTA、有示例证据；真实报告 3 张卡+买入成本、无 CTA、无幽灵线 | 用户导入真实账单后体验降级；“真实”反而不如“示例” | 把演示报告的核心视图移植到真实报告，而不是反过来 |
| 目标用户过宽 | 文档说“A 股个人投资者、年交易 10 次以上”；首页没有具体人设 | 痛点不聚焦；不知道为谁优化首跑 | 锁定“1–3 年经验、年交易 10 次以上、能导出券商 CSV 的活跃账户” |
| 第四卡口径混同 | 演示“标的自身涨幅 +18.92%”与“买入不动 +18.92%”相同；真实报告第四卡是“买入成本”；开发者报告写“口径未定义” | 无法证明“你选的股票本身在涨”；核心洞察失去证据 | 定义“股票本身涨幅”为独立口径（见 §3.4），否则删掉这张卡 |
| 规则候选“来自示例” | 规则页明写“3 条待处理 · 来自示例”；v3 要求“引擎按行为标签生成” | “规则共建”变成“选模板”，不是用户自己的模式 | 至少让候选来自已实现的追高模式；否则如实标注“示例候选” |
| “每个数字回到成交行”在真实报告不成立 | 首页承诺；真实报告只有已发布事实表（事实/结果/公式），没有成交行和完整 provenance | 可信度叙事与真实体验不一致 | 给真实报告加最小“查看来源”：公式 + 成交行 + 复核结论 |
| 口号不统一 | v2“股票/操作”、v3“选股/择时”、首页“差在哪里”、标题“照见成证据” | 品牌记忆点分散 | 一次定稿，全站/PPT/README 同步 |
| 真实报告没有 CTA | 演示报告底部有“写下一条规则”；真实报告没有 | 真实用户走不到“守住” | 在真实报告底部加同一个 CTA |
| 合规标签缺失 | 代码中没有“已过合规校验”；只有“本地数字校验通过”“在线复述” | v3 的零幻觉自证 UI 没有落地 | 用真实能证明的标签：“本地数字校验通过 · 不构成投资建议” |

### 2.4 建议的定位与首屏文案

**定位（对内）：** 用用户自己的交易记录，把“实际操作”和“买入不动”放在同一把尺上，算清差额、拆到每一笔；用户看见之后，可以自己写下一条规则，镜子只负责在下一次类似情境提醒。

**对外一句话：** 一个把择时损耗算到每一笔的交易行为分析智能体。

**首屏建议：**

- Slogan：你亏的不是股票，是操作。
- 主标题：同一笔本金，同一段行情：你的操作，和“买入不动”差多少？
- 副标题：差在哪一笔、为什么、下次要不要给自己立条规矩——都用你自己的账单说话。
- 主 CTA：导入账单，先看差距。
- 次 CTA：先看示例报告。
- 信任条：不荐股 · 不预测 · 不替你决定 · 原始 CSV 不上传。

**首跑路径（只保留一条）：** 导入 → 60 秒真实报告（幽灵线 + 四卡 + 差额）→ 问一句“我最错的一笔” → 可选“给自己立一条规矩”。

**人设：** 1–3 年经验、年交易 10 次以上、能从券商 APP 导出成交记录的 A 股个人投资者。

**边界：** 历史复盘，不是实时提醒；规则只做提醒，不下单、不阻止交易。

### 2.5 PPT 承诺与产品对应

| PPT 页 | 承诺 | 产品对应 | 一致性 |
|---|---|---|---|
| P2 目标用户/痛点 | 三问痛点、选股 vs 择时 | 首页有比较，但没有因果钩子和具体人设 | 部分 |
| P3 用户场景 | 幽灵对比线四指标卡 | 演示有，真实没有；第四卡失真 | 部分 |
| P4 产品方案 | 行为发现/反事实举证/规则共建 + Agent 能力条 | 行为发现无 UI；反事实只在开发者报告；规则是模板；Agent 只有一个问题 | 弱 |
| P5 技术方案 | 数据/计算/智能体/开发部署四层 | 模块存在，但用户不可见；部署不在阿里云 | 部分 |

## 3. 痛点审计

### 3.1 痛点链条

v2 的立项逻辑是一条完整的因果链：

1. 散户亏钱后，第一反应是“选错了股”。
2. 但多数散户选的股票本身在涨，是追涨、杀跌、早止盈、过度交易等操作把收益吃掉。
3. 券商复盘只展示“你赚了多少”，不展示“你本可以赚多少”，所以用户看不见这个差额。
4. 看不见，就无法归因；无法归因，就无法改变。
5. 镜子把差额算出来、拆到每一笔；用户看见后，自己立规矩；下一次类似情境，镜子提醒。

**这条链条是成立的，而且比“情绪化复盘”更具体、更可验算。**

### 3.2 够不够痛：分项判断

| 维度 | 判断 | 说明 |
|---|---|---|
| 频率 | 高 | 活跃账户反复发生，不是一次性事件 |
| 金额 | 高 | 直接是真金白银的差额，不是抽象评分 |
| 归因错误 | 高 | 用户以为是选股，实际可能是操作；反直觉，有冲击力 |
| 可量化 | 高 | 可用用户自己的成交记录算出来，且可复核 |
| 可行动 | 中 | 规则/提醒能提供行动路径，但当前只有模拟 |
| 输入摩擦 | 高 | 需要导出券商 CSV；小白用户可能卡在这一步 |
| 情绪阻力 | 高 | 亏损复盘本身令人回避；产品必须让“看见”足够快、足够安全 |
| 证据强度 | 中 | 宏观数字多数未核；用户自己的数据最强，但真实报告太薄 |

**结论：痛点真实且足够痛，但当前产品只把“痛”讲清楚了，没有把“这是我”证明出来，也没有把“怎么改”走完。** 具体表现为：

- 真实报告没有幽灵线，用户看不到“被操作吃掉的钱”长什么样。
- 第四卡“股票本身涨幅”缺位/混同，用户无法确认“我选的股票其实在涨”。
- 对话不能回答“我最错的一笔”，用户无法把差额归因到具体操作。
- 行为模式没有清单，用户无法知道“我是不是总在追高”。
- 规则候选是示例，不是从用户行为生成，用户感觉不到“这是我的规矩”。

### 3.5 一个关键的概念问题：第四张卡到底量什么

v2 想要“你选的股本身涨幅”，目的是证明“股票在涨，是操作吃掉了收益”。但当前演示中：

- 实际收益：+12.48%
- 买入不动：+18.92%
- 标的自身涨幅：+18.92%

第四张卡与第二张卡完全相同，说明它没有提供独立信息。真实报告则直接换成“买入成本”，开发者报告写“口径未定义”。这不是一个小缺口，而是**核心洞察缺少证据**。

要证明“选股没问题、操作有问题”，第四张卡应独立于“按用户实际买价持有”的幽灵收益，例如：

- **口径 A（期间涨幅）：** 每只标的从报告期首个交易日收盘价到估值日收盘价的涨幅，按买入成本或等权加权。它回答“这段时间这些股票本身涨了多少”，不包含用户的买入时点。
- **口径 B（首次买入持有）：** 每只标的从首次买入日收盘价到估值日收盘价的涨幅，按买入成本加权。它回答“从你第一次买入后，股票本身走了多少”，仍包含首次买入时点。
- **口径 C（等权组合）：** 组合内标的等权持有涨幅，剥离仓位大小的影响。

无论选哪个，都必须有 `formula_id`、数据来源、展示值和口径说明；并且要和“对照收益”明确区分。**建议在 10/21 内拍板，不能留到演示前。**

## 5. 已实现但没接出来（最高性价比）

这些不是“从零开发”，而是“把已有能力接到用户路径”，应优先于任何新模块：

1. **开发者报告的幽灵线**（`reportView.js` 的 `renderGhostChart`）→ 移植到真实报告。
2. **损耗分解引擎**（`decompose.js`）→ 生成真实报告的瀑布图/分解表。
3. **独立复核 + provenance**（`verify.js`/`provenance.js`）→ 真实报告加“复核通过/公式/来源”折叠区。
4. **planner 12 意图**（`planner.js`）→ 接真实对话，先放出 5 个芯片。
5. **行为发现引擎**（`behavior.js`，追高）→ 行为清单卡片 + “为什么追高”回答。
6. **S1 逐日序列**（`counterfactual.js`）→ “最错一笔”事实 + 单笔图。
7. **规则历史情境模拟**（`contractView.js`）→ 真实报告 CTA 后的演示入口。
8. **在线 intent/restate 路由**（`server/site-functions/handler.mjs`）→ 已存在，只差前端编排。

**判断：把 1–4 接出来，v2 的核心叙事就能站住；5–7 是第二层；8 是基础设施。**

## 6. 承诺与实现不一致（可信度风险）

| “每个数字回到成交行” | 真实报告只有事实/公式，没有成交行 | 可验算承诺落空 | 加最小来源展开 |
| “真 LLM 自由问答” | 只支持一个组合问题 | 任意提问会穿帮 | 先做 5 芯片 + 越界兜底 |
| “交易前提醒” | 历史情境模拟，不是实时 | 被问券商对接时无法回答 | 主动限定为“历史模拟” |
| “已过合规校验” | 只有本地数字校验 | 标签无法证明 | 改为“本地数字校验通过” |
| “买入不动”演示 | 静态示例估值，不是引擎实时算 | 被问“这是真算的吗”时弱 | 演示页标明“示例数据”；真实报告用引擎 |
| “真实行情” | 真实报告动态 Tushare；演示是示例估值 | 两套口径容易混淆 | 页面分别标注“示例/真实/动态/快照” |
| “原始 CSV 不上传” | 成立；但问题文本会发送 | 用户可能误解“全部本地” | 对话页明确“问题文本会发送” |

**原则：** 不能证明的标签不要用；不能端到端跑通的承诺不要放在首屏；演示替代要主动说明。
