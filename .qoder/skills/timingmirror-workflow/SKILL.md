# TimingMirror Qoder 工作流

## 角色和边界

Qoder 开发团队由 tm-lead、tm-quant、tm-ui、tm-dialogue、tm-review 组成。tm-lead 负责拆任务和汇总；tm-quant 负责实现确定性计算代码；tm-ui 负责实现展示和交互代码；tm-dialogue 负责实现产品对话链路代码；tm-review 只读审阅。这些都是开发助手，不承担产品业务功能，不随产品部署，也不假称桌面原生持久团队已创建。
普通小任务由主会话或单个执行角色完成。需要团队时主会话直接委派相应角色；tm-lead 若处于不可再派发的子代理上下文，只返回任务单。每个任务设置明确停止条件，不递归启动团队。

人类分工：changer 负责框架、接口、产品对话、派发任务和最终验收；尹辰负责数据计算；吴涵晶负责界面与契约交互。用户后续更正优先。

产品运行时能力和 Qoder 开发 Agent 是两层。TimingMirror 由项目代码独立运行；编排、复核和数字来源必须由确定性代码控制，产品代码调用 qwen-plus 做意图分类与事实 JSON 复述。三人各自在本机用 Qoder 开发，按需复用相同角色指令和 Skill，通过代码仓库交接；原生 Agent Team 只是可选开发工具，不要求共享调用或让负责人电脑为产品持续在线。

## 每轮问答协议

每次向 Qoder 提问都使用下面结构。新的设计选择由用户确认；已确认范围直接执行，不重复索要许可：

当前问题：
相关文件：
本轮允许修改的范围：
团队已确认的约束：
验收条件：

新方案先说明依据、最小方案和可能风险；已经确认的范围直接执行。实施后返回真实改动、验证命令、相关输出和剩余问题。

不要提前写出模型应该回答的内容。可以提前设计问题、文件范围和验收条件，但回答必须来自真实运行。

每轮保存以下关联信息：session_id、原始问题、选中的 Agent、用户确认、修改文件、git diff 或文件差异、验证命令及相关输出、任务前后 credits。首次实际开发任务用合成 CSV 验证会话记录落点；当前尚无工程时先做只读范围讨论，不创建工程或伪造会话。不要把 compact 摘要当原始会话。

## 12 个叙事轮次

1. 范围：从现有代码和提案中拆出最小闭环。
2. 能力核对：验证代码框架编排、意图分类、事实复述和复核是否落实。
3. 接口：冻结成交、行情、计算结果和证据引用的共享类型。
4. 计算：用可手算 fixture 验证实际收益、幽灵收益和损耗。
5. 反事实：单笔替换并展示双向结果。
6. 行为：检验标签、样本数、反例和证据不足路径。
7. 证据：把每个数字连回公式、行情和成交记录。
8. 对话：用未预设问题验证意图、事实 JSON、复述和校验。
9. 复核：用缺行情、超时和不一致 fixture 验证失败路径。
10. 规则：候选由确定性引擎生成，用户可以确认、改写、拒绝。
11. 审阅：tm-review 检查数字来源、隐私、合规和回归风险。
12. 交付：根据真实 session、diff、测试和用量整理 Qoder 使用说明。

第 2 轮是在验证既有产品决定，不得把“代码框架编排、qwen-plus 分类与复述”包装成新发现。

## 并发与接口约定

- 并行开发**不要求**八类接口全部冻结。
- 并行任务涉及共享字段/类型时（字段名与类型、金额/收益率/百分点单位、空值语义、一组脱敏合成样例），先由负责人确认该部分再并行。
- 最多两个执行 Agent 并行，且不能同时写同一文件。
- 共享类型发生变化时，暂停受影响的并行任务，回到 tm-lead 单 Agent 重新确认。
- 接口冻结完成度按轮记录在仓库文件与会话记录中；未受影响的模块不因冻结未完成而停止开发。

## Credits 节省规则

- 日常问答、格式调整和单元测试选择当前模型面板的较低费用选项；核心实现和高风险审阅才升级。模型继承桌面当前选择，不硬编码 CLI 档位。
- 分析任务先用只读或 Plan，再实施；先窄上下文后扩大范围；重复测试交给本地终端。Ask/Efficient 是部分入口名称，不能假定桌面有同名选项。
- 不为同一个问题同时启动普通 Subagent、Quest 和 Agent Team。
- 一次并行最多两个执行 Agent；Quest Experts 只有用户明确批准才使用。
- 桌面端在用量页面核对实际消耗；仅 CLI 使用 /usage。不要把估算表当固定价格。
- 团队控制目标为 9000 credits，保留 1800 应急；按账号、模型、有效期和任务分别记账。Qoder credits 与百炼推理费用分开记录。
- 阶段分配：范围 600、计算 2000、界面 1800、对话 1400、审阅 900、交付 500、应急 1800。已用到 5400 时重新估算，达到 7200 时只处理核心缺陷，1800 应急由负责人决定用途。这是工作约定，不是平台硬限额。

用 status 查看团队累计记账。record 记录用量页面中的任务前后“累计已用”数值，自动取差；需要账号代号、任务、session_id、模型、阶段和有效期。同一账号的并行任务按一个用量窗口统一记账，不能每个角色重复记同一段消耗；不记录登录信息，不推测用量。台账和角色并发上限是操作约定，不能自动阻止平台扣费。

当前目录包含的角色可用 install --project 已存在的真实工程路径安装为项目级配置，工具不会创建项目目录；项目配置不替代用户级原始会话。

## TimingMirror 硬约束

- 不荐股、不预测、不承诺收益、不替用户定规则。
- LLM 不生成金融数字；数字必须能回到本次事实 JSON、公式和原始交易记录。
- CSV、身份信息和凭证不进入 Qoder；使用合成或最小脱敏样例。
- 演示数字必须标为演示数据；证据不足就明确停止结论。
- 反事实归因保持双向，不能写成鼓励持有。
